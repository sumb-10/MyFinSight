# Module6. 모의투자와 운용 기록

전체 구조: [Module_prototype_v2.md](Module_prototype_v2.md)

## 1. 역할

이 모듈은 리포트에서 선택한 전략을 가상 자본으로 시작하고, 이후 자료가 들어올 때마다 성과를 기록한다. 리밸런싱일에는 같은 포트폴리오 구성 함수를 사용해 비중을 조정한다. 실제 주문과 계좌 연결은 수행하지 않는다.

과거 백테스트는 전략의 과거 평가이고, 모의투자는 사용자가 등록한 날짜 이후의 가상 운용이다. 두 결과를 한 곡선으로 이어 붙이지 않는다.

## 2. 입력과 출력

| 구분 | 내용 |
| --- | --- |
| 입력 | 기준 리포트·전략, 시작일, 가상 자본·통화, 적립·리밸런싱 규칙, 시작 조건과 DB 자료 |
| 출력 | 가상 보유 자산, 일별 평가 기록, 리밸런싱 기록, 목록·상세 화면용 결과 |
| 연동 | Module2의 가격·환율·뉴스, Module4의 `construct()`, Module5의 공통 성과 계산, Module7의 화면 |

## 3. 시작과 상태 관리

사용자가 리포트에서 전략을 선택하면 기준 리포트, 시작일, 가상 초기자본, 통화, 종목·비중과 적립·리밸런싱 규칙을 보여 준다. 확인 버튼을 누른 뒤에만 별도 `paper_id`를 발급하고 등록한다. 시작 전에는 평가와 리밸런싱을 수행하지 않는다.

시작 비중은 기준 리포트의 현재 구성에서 가져온다. 시작일이 분석 기준일보다 늦으면 그 시작일 자료로 Module4를 다시 호출한다. 이때 시작 확인 화면에 재구성된 비중과 기존 비중의 차이를 보여 준 뒤 최종 확인해야 한다. 실제 적용 비중이 확인한 화면과 다르지 않게 한다.

시작일의 가용 가격으로 소수 주식·수수료 가정에 따라 매수하고 첫 평가 기록을 저장한다. 비거래일의 시작 날짜를 실제 거래일로 바꾸는 규칙과 거래 시점은 확정이 필요하다. 시작일은 DB 데이터 마감을 넘을 수 없다. 기본 입력이 오늘이더라도 오늘 자료가 아직 없으면 가능한 날짜를 안내하고 미완성 가격으로 시작하지 않는다.

같은 리포트·전략을 여러 번 등록할 수 있고 각 등록은 별도 ID를 갖는다. 등록해도 원본 리포트와 백테스트는 바뀌지 않는다. 프로필이 나중에 수정되어도 등록 당시 조건은 그대로 사용한다.

사용자가 중지하면 평가와 리밸런싱을 멈추고 보유를 유지한다. 재개하면 중지 기간의 일별 기록은 비워 두고 재개일부터 갱신한다. 중지 중 지나간 리밸런싱은 실행하지 않고 건너뛴 기록을 남긴다. 비어 있는 기간을 연속 운영한 것처럼 연결하지 않는다.

## 4. 일별 갱신과 리밸런싱

### 새 거래일 처리

가격 적재 완료 후 서버가 갱신하거나 사용자의 새로고침 요청으로 실행한다. 마지막 처리일 다음 거래일부터 데이터 마감까지 날짜순으로 처리한다. 반복 실행해도 같은 날짜가 중복 저장되거나 가상 매수가 두 번 발생하지 않아야 한다.

각 날짜에는 기존 보유의 평가, 적립금 반영, 필요한 리밸런싱, 비용 반영과 최종 평가 기록을 하나의 순서로 처리한다. 현금흐름과 체결 시점은 Module5와 같게 정의한다. 하루를 처리하는 동안 사용한 가격·환율·목표 비중과 거래를 연결해 기록한다.

평가액은 보유 수량과 적용 가격으로 계산하고 현금을 더한다. 환율은 Module2의 같은 날짜 정책을 사용한다. 비교지수도 동일한 초기자본과 적립으로 평가한다. 성과 계산은 Module5의 공통 함수를 사용하며 적립금을 수익으로 계산하지 않는다. 1년 미만의 연환산 지표는 참고 값으로 표시한다.

### 리밸런싱

리밸런싱일은 시작 시 확정한 규칙으로 계산한다. 해당 날짜의 자료가 준비된 뒤에만 처리한다. Module4의 `construct()`에 종목, 구성일과 저장된 조건을 전달해 새 목표 비중을 얻는다.

종목은 유지하고 비중만 갱신한다. 뉴스 기반 조정을 사용하는 전략은 직전 14일의 DB 뉴스와 BL을 사용하며, 뉴스가 부족하면 기준 비중으로 돌아간다. 뉴스 조정이 꺼진 전략이나 특정 템플릿을 선택한 전략에는 그 전략의 구성 방식만 적용한다. 모든 모의투자를 BL 전략으로 바꾸지 않는다.

현재 비중에서 목표 비중으로 가상 거래하고, 조정 전·목표·실제 적용 비중을 각각 저장한다. 수수료, 회전율, 거래 수량과 가격, 사용한 의견과 근거, 대체 처리 여부도 남긴다. 백테스트와 같은 체결·휴장일 정책을 사용한다.

### 데이터 지연

필수 가격이나 환율이 아직 없으면 그 날짜의 최종 평가 기록을 만들지 않고 갱신을 보류한다. 품질 검사로 제외된 가격을 임의로 직전값에 붙여 정상 완료로 처리하지 않는다. 정상 휴장일 가격 유지와 자료 누락은 Module2의 구분을 따른다.

화면에는 지연 상태와 마지막 성공 기준일을 반환한다. 여러 거래일이 밀렸다면 누락 자료를 확보한 뒤 날짜순으로 처리한다. 화면 새로고침은 갱신 요청이며 즉시 최신 가격이 생긴다는 약속이 아니다.

## 5. 저장 객체

저장 위치는 `store/data/paper/<paper_id>/`다. 모든 객체는 `schema_version`을 포함하고 공통 `store.py`를 통해 저장한다.

| 파일 | 핵심 필드 |
| --- | --- |
| `portfolio.json` | paper·report·run·strategy ID, 전략명, 시작일, 초기자본, 적립, 리밸런싱, 조건 스냅샷, 종목, 시작 비중, 현재 보유·현금, 상태와 이력 |
| `snapshots.jsonl` | 날짜, USD 평가액·현금, 비중, 낙폭, 시작 이후 운용 수익률, 당일 적립, 비교지수 평가액, 환율과 상태 |
| `rebalances.jsonl` | 날짜·순번, 조정 전·목표·적용 비중, 거래, 수수료, 회전율, 의견·근거, 뉴스 구간, fallback·skipped·문제 기록 |

초기자본은 원래 금액·통화와 USD 환산값·환율·환율 날짜를 함께 보관한다. 보유 상태는 종목별 수량, USD 현금과 마지막 평가일을 갖는다. ID 형식은 `paper_<YYYYMMDD>_<4hex>`다.

JSONL은 날짜당 최종 평가 한 줄, 리밸런싱당 한 줄을 추가하고 과거 줄을 수정하지 않는다. 저장 도중 실패했을 때 일별 기록과 현재 보유가 서로 어긋나지 않도록 처리 완료 기준과 복구 방식을 정해야 한다. 재시도는 날짜·순번으로 이미 처리된 사건을 확인한다.

모의투자 상태는 운영 여부인 active·stopped와 갱신 상태인 ok·delayed를 구분한다. 원문에는 snapshot 상태 hold도 있으므로 실제 저장 시 의미를 확정해야 한다. 자료가 없는 날짜의 지연 상태를 표시하기 위해 정상 평가액을 가진 가짜 스냅샷을 만들지 않는다.

## 6. 화면에 제공하는 정보

목록에는 전략명, 시작일, 최신 기준일, 가상 초기자본과 현재 평가액, 시작 이후 운용 수익률, 같은 기간 비교지수와의 차이, 갱신 상태를 반환한다. 납입 합계와 자산 증가액도 운용 수익률과 구분해 제공한다.

상세에는 다음 내용을 담는다.

- 모의투자 시작 이후의 성과와 비교지수
- 별도의 과거 백테스트 결과
- 시작·현재·목표·리밸런싱 적용 비중
- 적립과 리밸런싱 규칙, 거래·비용·근거 기록
- 중지·재개·건너뛴 리밸런싱 이력
- 데이터 마감과 마지막 성공 기준일

시작일이 다른 전략을 같은 기간 성과처럼 순위화하거나 합산하지 않는다. 낙폭 사건은 정보로 표시하고 별도 자동 매매 신호로 사용하지 않는다. 결과 조회에서는 기록을 임의로 다시 계산하지 않고 저장된 수치와 지표를 사용한다.

## 7. 구현 상태와 완료 기준

원문에서 이 모듈은 전체가 설계 단계다. Module4의 구성 함수, Module5의 현금흐름·지표 정의와 공통 저장 계층이 준비된 뒤 연결한다. 서버 배치가 가동될 때 브라우저를 닫아도 갱신할 수 있으며, PC가 꺼지거나 서버가 멈춘 동안의 즉시 갱신은 보장할 수 없다.

- 명시적으로 확인한 조건과 시작 비중이 실제 적용값과 일치한다.
- 같은 날짜의 반복 갱신이 평가·적립·매매를 중복시키지 않는다.
- 리밸런싱이 선택한 전략을 유지하며 종목은 바꾸지 않는다.
- 자료 누락 시 마지막 성공 날짜와 지연 상태가 드러난다.
- 납입금과 운용 수익률이 분리되고 비교지수에 같은 납입 조건이 적용된다.
- 과거 백테스트와 모의투자 성과, 중지 기간이 화면에서 구분된다.

확인할 항목은 비거래일 시작 처리, 시작일이 분석 기준일보다 이른 요청의 처리, 중지 기간의 성과 계산 방식, 하루 처리 중단 시 복구와 전략별 현재 구성의 ID 연결이다.
