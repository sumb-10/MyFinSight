# Module2. 금융 데이터 관리

전체 구조: [Module_prototype_v2.md](Module_prototype_v2.md)

## 1. 역할

이 모듈은 분석에 필요한 금융 자료를 조회하고, 각 단계가 사용할 수 있는 형태로 정리한다. 데이터 품질과 기준일을 확인하고 종목 검색 정보, 뉴스 근거와 출처를 함께 제공한다.

자료 수집은 팀의 수집 배치가 맡는다. 분석 코드는 팀 PostgreSQL만 읽으며, 자료가 없을 때 외부 사이트나 yfinance를 호출해 보충하지 않는다. 로컬 parquet는 조회 성능을 위한 캐시이고, 원천 자료는 DB다.

## 2. 입력과 출력

| 구분 | 내용 |
| --- | --- |
| 입력 | 종목 또는 지수, 조회기간, 분석 기준일, 필수 종목, 품질 기준 |
| 출력 | 가격·환율·재무 패널, 구성종목, 종목 검색 사전, 뉴스 근거, 품질 보고와 데이터 마감 |
| 사용처 | Module1의 요청 준비, Module3의 검색·선정, Module4의 추정·투자 의견, Module5의 백테스트, Module6의 평가 |

## 3. DB 자료와 수집 계약

대상은 미국의 S&P 500·NASDAQ-100과 한국의 KOSPI 200이다. 미국 종목은 USD, 한국 종목은 KRW 가격으로 저장한다. 계산 단계에서는 모두 USD로 환산한다.

| 테이블 | 키 | 분석에 필요한 최소 필드 |
| --- | --- | --- |
| `assets` | `asset_id` | ticker, name, market, currency, yfinance_symbol |
| `index_constituent` | index_code·snapshot_date·ticker | name, sector, industry |
| `price_daily` | asset_id·date | open, high, low, close, adj_close, volume |
| `fx_daily` | pair·date | rate: 1 USD당 KRW |
| `financials` | asset_id·period_end·statement·item | value, 보고일 |
| `news` | news_id | asset_id, source, url, title, content, publisher, published_at, language |

DB 지수 코드는 SP500·NDX·KOSPI200이고, 요청의 NASDAQ100은 NDX로 매핑한다. 자산 ID는 `US-<ticker>` 또는 `KR-<6자리 종목코드>`로 구분한다. 미국 티커는 `BRK-B`와 같은 표기를 사용한다. 한국 종목코드와 외부 조회 기호의 관계는 `assets`에서 관리한다.

수집 배치는 시장별 마감 후 가격, 일별 환율, 분기 재무, 구성종목 변경과 뉴스 자료를 적재한다. 실제 구성종목 변경일과 수시 변경은 수집기가 관리한다. 분석 코드에 모든 지수의 변경 일정을 하나의 규칙으로 고정하지 않는다. 같은 키는 값이 달라질 때만 갱신하고, 날짜 단위로 일관된 자료가 조회되도록 커밋한다.

수집 상태는 팀 수집기의 `fetch_log`에서 읽는다. 소스, 대상, 기간, 상태, 수집 시각과 오류를 기록하고 최신 성공 날짜를 데이터 마감에 사용한다. `fetch_log`는 수집 측 계약이며 서비스 저장 테이블 추가 결정과 별개다.

사업 설명, 발행주식수, EPS·ROE·배당과 비교지수 가격도 후속 계산에서 필요하다. 위 최소 필드만으로 모두 제공되는 것은 아니므로 실제 DB 항목과의 매핑을 확인해야 한다.

## 4. 조회와 품질 검사

### 기준일 적용

모든 조회는 호출자가 지정한 기준일을 넘지 않아야 한다. 가격은 해당 시점까지의 이력을, 재무는 해당 시점에 보고된 자료만 반환한다. 재무기간 종료일이 과거라는 이유만으로 아직 발표되지 않은 자료를 사용할 수 없다.

가격 패널에는 수익률·백테스트용 `adj_close`와 주가 기반 지표용 `close`를 구분한다. 한국 가격은 날짜별 환율로 USD 환산한다. 환율 조회는 지정일 또는 그 이전의 사용 가능한 값을 반환하며 환율 날짜와 출처를 남긴다.

### 결측과 이력 부족

종목별 커버리지는 기대 거래일 중 실제 가격이 있는 비율이다. 기본 통과 기준은 95%다. 연속 한 거래일의 결측만 직전값으로 채우고 `FILLED`로 기록한다. 커버리지가 95% 미만이거나 두 거래일 이상 연속 결측이 있으면 종목을 제외하고 사유를 남긴다.

비교지수와 필수 포함 종목처럼 필수로 지정된 자산이 제외되면 해당 분석을 중단한다. 사용 가능한 종목이 하나도 남지 않아도 중단한다. 최종 패널에는 NaN이 없어야 하며, 제외·보간 정보는 결과와 리포트로 전달한다.

이력 길이는 사용하는 단계가 지정한다. 종목 선정에는 기준일 전 400달력일 이상의 가격 이력을, 시장모형에는 추정 창 안 최소 252개 수익률을 요구한다. 신규 상장 이전 기간은 일반 결측과 구분해야 하며, 이 조건의 세부 계산 범위는 구현 시 일치시켜야 한다.

### 혼합 시장 달력

기존 설계안은 미국과 한국 거래일의 합집합을 사용한다. 한 시장의 정상 휴장일에는 마지막 현지 가격을 유지하고 `HOLIDAY_HOLD`로 기록한다. 이는 데이터 누락을 보간한 경우와 구분하며 커버리지 계산에서 제외한다. KRW 자산의 USD 평가에는 해당 날짜에 적용한 환율도 함께 기록한다.

이 방식은 미확정 정책이다. 휴장일에 가격을 유지하는 것과 실제 가상 거래가 가능한지는 다른 문제이므로, 휴장 자산의 주문 이월 및 시장별 마감 시각은 Module5·6과 함께 정해야 한다. 합집합 달력에 연 252일을 적용하는 가정도 성과 지표에 표시한다.

## 5. 종목 검색용 사전

종목마다 산업분류, 키워드와 한 줄 소개를 정리한다. 기존 코드에서 부르는 디스크립터는 이 검색용 사전이다. Module3은 산업 코드와 키워드로 후보를 찾기 때문에 LLM이 종목 전체 목록을 직접 검색할 필요가 없다.

GICS는 섹터·산업그룹·산업·세부산업의 네 단계이고 코드는 각각 2·4·6·8자리다. DB의 산업명을 `data/reference/gics_taxonomy.json`과 연결해 정규화한다. 한국 종목은 KRX 업종에서 GICS로 옮기는 매핑표를 작성하고 검수해야 한다. 이 매핑은 기존 명세에서도 미확정 항목이다.

소개 문장은 선택적으로 생성한 LLM 한국어 요약, DB 사업 설명의 첫 문장, 회사명과 세부산업을 결합한 기본 문장 순으로 사용한다. 어떤 자료로 만들었는지 종목별로 기록한다. LLM 요약을 쓰더라도 입력 자료에 없는 사업 사실을 추가하지 않는다.

구성종목 스냅샷이 바뀔 때마다 사전을 재생성하고 날짜별 버전을 보관한다. 과거 분석에는 기준일 이전의 가장 최근 버전을 사용한다. 분석 중에 버전을 바꾸지 않고, 한 실행이 사용할 버전 목록을 고정한다.

당시 구성종목 기록이 없으면 기존 결정대로 가장 오래된 확보 버전을 사용하되, “당시 구성종목 미확보”을 기록한다. 이 예외는 당시 자료만 사용한 분석과 같지 않다. 사업 설명과 산업분류의 시점도 보장되지 않으면 추가 한계로 남긴다.

사전에는 티커, 이름, 시장과 통화, 네 단계 산업 코드·이름, 키워드, 소개와 출처를 담는다. 산업 접두 코드 검색, 단어 경계 기반 키워드 검색, 섹터명 변환과 상위 분류 조회를 지원한다. 결과는 `data/processed/<universe>_descriptor.json` 계열의 날짜별 버전으로 저장한다.

## 6. 뉴스·공시 근거 제공

(2026-10-25 라운드 4) 근거 창은 뉴스 14일 + **공시 45일** 두 창을 함께 가진다(`EvidenceWindow`). 공시는 `disclosures` 표에서 `available_on ∈ [d−45, d)`, 수정 공시 제외, 사건 종류 허용 목록(실적·자사주·배당·합병·주요 계약·증권 발행·경영권 변경·소송·풍문 답변·시설투자·구조조정 등 26종; ELS·대량보유·위임장·관계자 거래·주총·첨부만 등은 제외)으로 읽고, 종목별로 사건 중요도 → 최신순 상한(8건)을 둔다. 근거 ID 는 `dc<disclosure_id>`, 날짜 기준은 이용 가능일이다. SEC 공시의 제목은 "8-K" 뿐이라 양식·항목·사건 라벨을 합쳐 "8-K 2.02,9.01 · 실적 발표"로 보여 준다(`disclosure_labels.py`, 수집기 규칙의 모든 사건 종류에 한국어 라벨). "근거 부족 → 기준 비중" 판정은 뉴스 **또는** 공시가 있는 종목 수로 한다. 06 기업 근거·14c 시장 분석에는 90일 사건 요약(정기 보고 포함)을 준다.


종목과 기간을 받아 `news`와 `assets`를 연결해 조회한다. 기본 언어는 미국 종목 영어, 한국 종목 한국어다. DB에 소스가 추가되면 설정으로 반영한다.

조회 구간은 시작 포함·끝 제외인 `[start, end)`다. 제목의 대소문자를 정규화해 중복을 제거하고, 최신순으로 종목당 최대 건수를 반환한다. 구성 단계의 기본값은 종목당 10건이며, 기준일 직전 14일을 사용한다.

| 근거 필드 | 내용 |
| --- | --- |
| `evidence_id` | `ev<news_id>` |
| `ticker`, `published_at` | 관련 종목, UTC 발표 시각 |
| `source`, `publisher` | 데이터 소스, 발행기관 |
| `title`, `excerpt`, `url` | DB 제목, 사용한 발췌, 원문 링크 |
| `origin` | db |

출처 패널에는 문서명, 발행기관, 발표일, 발췌와 원문 링크를 제공한다. 제목·본문·URL은 DB 값에서 가져오고 LLM이 만들게 하지 않는다.

날짜 구간을 UTC 발표 시각으로 변환하는 기준은 시장별 시차 정책과 일치해야 한다. 단순히 날짜 문자열만 비교해 구성 시점 이후 뉴스를 포함시키지 않는다.

## 7. 구현 연결

DB 접근은 공통 `db.py`로 모은다. 주요 함수는 `prices_panel(tickers, start, end)`, `fx_on_or_before(pair, date)`, `financials_asof(tickers, as_of)`, 기준일별 구성종목 조회, `news_window(...)`다. 과거 구성종목 조회는 최신 목록만 반환하는 함수와 구분한다.

과거 데이터 정정도 반영할 수 있도록 최신 날짜 외의 갱신 정보가 필요한지는 확인한다. 분석 코드에는 읽기 계정만 제공한다.

기존 `build_descriptor.py`, `descriptor.py`, `stage0_descriptor_llm.py`를 사전 생성에 재사용하고 `news_db.py`는 공통 DB 계층에 통합한다. 개발용 `fetch_data.py`와 `fetch_fundamentals.py`는 서비스 분석 경로에서 호출하지 않는다.

## 8. 완료 기준과 확인 사항

- 반환 자료가 기준일과 뉴스 구간을 넘지 않는다.
- 커버리지 0.95는 통과하고 0.9499등 그 이하는 제외된다.
- 결측 보간과 정상 휴장일 유지가 구분된다.
- 필수 종목 자료가 없으면 원인과 함께 중단한다.
- 과거 구성종목 버전과 자료 부족의 한계가 결과에 남는다.
- 모든 뉴스 인용이 실제 DB 근거와 연결된다.

조회 통일, 품질 검사, 한국 종목 사전과 한국어 뉴스는 원문에서 보완 대상으로 기록되어 있다. 수집 배치는 팀 DB 담당의 범위다. 혼합 시장 달력·환산·체결 시점, KRX→GICS 매핑, 재무·발행주식수·비교지수 제공 범위를 구현 전에 확인해야 한다.
