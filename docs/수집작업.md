# 수집 작업 (collectors/, jobs/daily.py)

GitHub Actions 가 예약 실행하는 역할 A 정기 수집. 예약 시각은 `.github/workflows/collect.yml`.

## 1. 작업

| 작업 | 명령 (PC) | 하는 일 | 저장 테이블 |
|---|---|---|---|
| prices | `python -m backend.jobs.daily prices` | 출처 줄(2절)마다 ① 그 출처로 받은 데이터의 최근 10일 증분 ② 그 출처로 아직 N년치가 없는 종목 백필. 환율(KRW=X)은 yfinance 줄에서. 남은 시간에 교차검증 | price_daily_source → price_daily (발행), fx_daily, assets, fetch_log |
| meta | `python -m backend.jobs.daily meta` | 정기 변경일이 지났으면 구성종목 갱신. 이어서 GICS 분류 맞춤 (7절, 새 종목 KSIC 60·사업 설명 30개까지). 재무는 마지막 성공이 7일 넘은 종목부터 하루 120종목 (약 720종목을 7일에 한 바퀴). 처음 받는 종목은 FIN_YEARS(12)년 전체, 이미 받은 종목은 작년 1월 1일부터만. 이어서 주식 분할 이력(yfinance), 남은 시간에 가치평가 증분 | index_constituent, assets (GICS 칸 포함), gics_taxonomy, financials_source → financials (발행), fetch_log |
| news | `python -m backend.jobs.daily news` | 출처 줄마다 오래 안 받은 종목부터 하루 한도만큼, 종목·날짜당 최대 5건. NEWS_KEEP_DAYS(4000일) 지난 기사 삭제 (0 이하면 지우지 않음) | news, fetch_log |
| disclosures | `python -m backend.jobs.daily disclosures` | 종목마다 최근 14일 공시 (SEC EDGAR submissions·DART 공시검색), 하루 한 번. 유형은 collectors/disclosures/categories.py (규칙을 바꾸면 `backend/scripts/reclassify_disclosures.py`). 첫 수집은 `backend/scripts/backfill.py --what disclosures --disclosure-from 2000` | disclosures, fetch_log |
| valuation | `python -m backend.jobs.daily valuation` (`--full` = 전체 다시 계산) | 가격·재무가 바뀐 종목·날짜만 다시 계산해 바뀐 행만 씀 (5절). prices·meta 끝에도 남은 시간에 자동으로 | valuation_daily, fetch_log |
| verify | `python -m backend.jobs.daily verify` | 출처 간 교차검증 (3절). prices 끝에도 자동으로 이어서 함 | price_daily_source, price_daily (verify_status) |
| all | `python -m backend.jobs.daily all` | prices·meta·news 차례로 | |
| (긴 백필) | `python backend/scripts/backfill.py` | PC 에서 몇 시간~며칠: GICS, 재무 12년, 가치평가, 뉴스 최대한 (6절) | 위 테이블 전부 |
| (사전) | `python backend/scripts/build_descriptor.py` | DB 만 읽어 종목 검색용 사전 파일을 만듦 (8절) | 없음 (`backend/data/processed/*.json`) |

공통 규칙:

- 한 번 실행은 시간 예산(`--budget`, 기본 480초, Actions 는 1020초) 안에서 끝남. 출처(KIS·Alpaca·yfinance·Tiingo)를 동시에 50종목씩 처리하고(Alpaca·yfinance 는 여러 종목을 한 요청으로), 남은 시간에 교차검증. 남은 일은 다음 실행이 이어 받음. 결과의 `done: false` 가 "남은 일 있음".
- 진행 상황은 DB 가 기억함 (가격은 출처별 저장 범위, 나머지는 `fetch_log`). 커서·상태 파일 없음.
- 같은 종목이 성공 기록 없이 3번 실패하면(상장폐지 등) 백필·재무 대상에서 빠짐.
- 늦게 상장한 종목은 백필 범위를 덮는 요청이 한 번 성공하면 끝난 것으로 봄 (그 전 데이터가 없으므로).
- 한국·미국 종목은 따로 묶어 받음 (한 PriceFrame 은 한 통화, DB_설계 6절).
- 키가 없는 출처는 건너뛰고 결과 `notes` 에 남김.

대상 종목 = 저장된 최신 구성종목 (`UNIVERSE_INDICES`) + `EXTRA_TICKERS` + `BENCHMARK_TICKERS` + `ETF_TICKERS`.
처음 실행 때 구성종목이 없으면 prices 가 먼저 받아 옴.

설정 (`.env`, 비우면 기본값):

| 키 | 기본값 | 뜻 |
|---|---|---|
| `UNIVERSE_INDICES` | `SP500,NDX,KOSPI200` | 구성종목을 받을 지수. KOSPI200 은 `backend/data/config/kospi200.csv`, 없으면 `backend/data/config/kospi200_krx.csv` + `backend/data/config/kr_gics.csv` (4절) |
| `EXTRA_TICKERS` | (없음) | 더 받을 종목. `005930.KS:삼성전자` 처럼 `티커:뉴스 검색어` |
| `BENCHMARK_TICKERS` | `SPY,QQQ` | 벤치마크. 가격만 받음, `assets.asset_type = ETF` |
| `ETF_TICKERS` | (없음) | 벤치마크 밖 ETF. 가격만 받음, `asset_type = ETF`. 전략 쪽은 `asset_type = 'STOCK'` 으로 ETF 를 뺌 |
| `BACKFILL_YEARS` | `1` (`.env.example` 은 10) | 가격 백필 연수. 운영 정기 수집은 10년, 운영 DB 에는 PC 긴 백필로 1999-10 부터 있음 |
| `FIN_YEARS` | `12` | 재무 받는 연수. 10년치 TTM(PER·ROE) 계산에 앞 1~2년이 더 필요해 12. 운영 DB 는 미국 2005~, 한국 DART 2015~ + KIS_FIN 2004~2014 |
| `VALUATION_YEARS` | `10` | valuation_daily 계산 연수 (운영 DB 는 `--valuation-full` 로 1999-10 부터) |
| `DART_SHARE_REPORTS` / `DART_DIVIDEND_REPORTS` | 네 보고서 모두 / `11011` | DART 주식 총수·배당을 받을 보고서 (요청 수를 줄이려면 `11011` 만) |
| `FIN_REFRESH_DAYS` | `7` | 재무 다시 받는 주기 |
| `NEWS_PER_TICKER_DAY` | `5` | 종목·발행일당 최대 기사 수 |
| `NEWS_KEEP_DAYS` | `4000` | 기사 보관 일수 (약 11년). 0 이하 = 영구 보관. **운영은 0** (`collect.yml` 이 덮어씀, 2005년 기사부터 보관) |
| `NEWS_DAILY_LIMITS` | `NAVER_NEWS=200,GOOGLE_RSS_KR=200,GOOGLE_RSS_US=200,NEWSAPI=90,ALPACA_NEWS=200` | 뉴스 줄별 하루 요청 종목 수 (NewsAPI 무료 하루 100회). 0 = 그 줄 끔 |
| `NEWS_RSS_INTERVAL_SEC` | `1.5` | 백필의 Google News RSS 요청 간격(초) |
| `NEWSAPI_DAILY_MAX` | `100` | 백필이 쓰는 NewsAPI 하루 한도 (오늘 이미 쓴 요청을 빼고 씀) |
| `PRICE_SOURCES` | `KIS,ALPACA,YFINANCE,TIINGO` | 가격을 받을 출처 줄 (2절). 빼면 그 출처는 안 부름 |
| `TIINGO_DAILY_SYMBOLS` | `15` | Tiingo 표본 줄이 하루에 받는 종목 수 (무료: 한 달 서로 다른 종목 500개) |
| `PRICE_PRIORITY_US` | `ALPACA,TIINGO,YFINANCE` | 미국 가격을 읽을 때 같은 날 출처가 여럿이면 고르는 순서 |
| `PRICE_PRIORITY_KR` | `YFINANCE,KIS` | 한국 **수정종가** 를 고르는 순서. 종가·OHLCV 는 코드 고정 `KIS → YFINANCE` (2절) |

뉴스 줄: `NAVER_NEWS`·`GOOGLE_RSS_KR` 은 한국 종목(검색어 = 이름), `NEWSAPI`·`GOOGLE_RSS_US` 는 미국 종목(검색어 = 구성종목 이름), `ALPACA_NEWS` 는 미국 종목(검색 = 티커, Benzinga 기사, ALPACA 키 사용).


## 2. 출처: primary 와 secondary

원칙: 공식 API 를 primary 로 두고, 나머지는 보완·교차검증(secondary)으로 씀. 요청은 모든 출처에 함.

| 데이터 | Primary (공식) | Secondary (보완·교차검증) | 수집 작업 |
|---|---|---|---|
| 한국 가격 | 한국투자(KIS) | yfinance | prices: `KIS` 줄, `YFINANCE` 줄 |
| 미국 가격 | Alpaca | yfinance, Tiingo(표본) | prices: `ALPACA` 줄, `YFINANCE` 줄, `TIINGO` 줄 |
| 환율 USD/KRW | (공식 없음) | yfinance `KRW=X`, FRED `DEXKOUS` (yfinance 없는 날) | prices: `YFINANCE` 줄 (US 실행) |
| 한국 재무 | DART (2015 사업연도~) | KIS 연간 재무 `KIS_FIN` (2004~2014, PC 백필 한 번) | meta |
| 미국 재무 | SEC EDGAR | 없음 | meta |
| 한국 뉴스 | 네이버 | Google RSS | news: `NAVER_NEWS`, `GOOGLE_RSS_KR` |
| 미국 뉴스 | NewsAPI, Alpaca News | Google RSS | news: `NEWSAPI`, `ALPACA_NEWS`, `GOOGLE_RSS_US` |
| 구성종목 | (공식 무료 API 없음) | 미국: 위키백과, KOSPI200: KRX 내려받기 파일 (4절) | meta |

가격 줄:

| 줄 | 역할 | 대상 | 하는 일 |
|---|---|---|---|
| `KIS` | primary | 한국 종목·ETF | 6자리 코드로 요청, `005930.KS` 표기로 저장. 증분 + 백필 |
| `ALPACA` | primary | 미국 종목·ETF | 증분 + 백필 (무료: 분당 200회, 2016년 이후, SIP 이력은 최근 15분만 제외) |
| `YFINANCE` | secondary | 전 종목 + 환율 | 증분 + 백필. 배당 반영 수정종가와 환율 공급 |
| `TIINGO` | 표본 | 미국 종목 | 토요일 주간 실행 때 75종목(`--sample 75`)을 오래 안 받은 순으로 돌아가며 최근분만 (무료 한도: 시간당 50회, 하루 1,000회, 한 달 서로 다른 종목 500개) |

- 출처마다 `price_daily_source` 에 따로 행이 쌓임 (키 `(ticker, date, source)`). 출처별 비교가 가능함.
- 같은 트랜잭션에서 (종목, 날짜) 마다 한 행을 골라 계약 테이블 `price_daily` (키 `(asset_id, date)`) 에 발행함: 통화별 우선순위 → 수집 시각 늦은 순 (CONSENSUS 행은 값으로 쓰지 않고 `verify_status` 만 가져옴). `get_prices` 는 이 발행 테이블을 읽음.
  - 미국: `ALPACA → TIINGO → YFINANCE`. 셋 다 분할+배당 보정 수정종가.
  - 한국: 종가·OHLCV·거래량은 `KIS → YFINANCE` (`source` 칸), 수정종가는 `YFINANCE → KIS` (`adj_close_source` 칸). KIS 수정주가는 배당을 반영하지 않아 수익률 계산용 수정종가는 yfinance 를 먼저 씀.
- 어디까지 받나: 실행 시각에 장이 끝난 날까지 (`update.closed_through`: 한국 16:00 KST, 미국 16:30 동부 시각 뒤면 그날, 전이면 전날). 16:37 KST 한국 실행은 그날 종가까지 받음 (2026-10-16 까지는 "UTC 어제"까지만 받아 한국 값이 하루 늦었음).
- 출처 간 교차검증(`data/verify.py`)은 prices 실행이 수집을 끝낸 뒤 남은 시간에 이어서 함. 3절.
- 서비스 요청 때 부족분을 바로 받는 인스턴스 API 의 `/prices` 는 yfinance 하나로 채움 (빠른 응답용). 나머지 출처는 다음 prices 실행이 채움.
- Tiingo 유료(Power 월 $30)는 개인 용도 전용이라 서비스 표시에 맞지 않고, primary 가 무료 Alpaca 라 쓰지 않음.

하루 요청 수 (대상 약 723종목: 미국 518 + 한국 201 + ETF 3):

| 출처 | 1건당 요청 | 하루 요청 수 | 출처 한도 |
|---|---|---|---|
| KIS | 종목당 100거래일마다 1회 (증분은 1회) + 토큰 | 약 202회 (백필 때 종목당 약 13회) | 초당 20회 (실전 계좌) |
| Alpaca | 종목당 2회 (분할 보정, 전체 보정) | 약 1,040회 (520종목) | 분당 200회 |
| yfinance | 종목당 1회 | 한국 약 202회(매일) + 미국 약 520회(토요일) + 환율 1회 | 공식 한도 없음 |
| Tiingo | 종목당 1회 | 주 75회 (토요일) | 하루 1,000회, 한 달 500종목 |
| DART | 처음: 회사당 약 105회 (12년 × 주요계정 4종 + 주식 총수 4종 + 배당 1종). 갱신: 회사당 약 15회 (작년·올해) | 처음 받을 때만 많음, 그 뒤 한국 종목 수 × 15 (7일마다) | 하루 2만 회 |
| SEC EDGAR | 종목당 1회 | 하루 최대 120회 (재무 하루 상한을 한국·미국이 나눠 씀) | 초당 10회 |
| 네이버 뉴스 | 종목당 1회 | 한국 종목 수 | 하루 2만5천 회 |
| NewsAPI | 종목당 1회 | 최대 90회 | 무료 하루 100회 |
| Alpaca News | 종목당 1회 이상 (50건마다 1쪽) | 최대 200종목 | 분당 200회 |
| Google RSS | 종목당 1회 | 한국 + 미국 최대 200회 | 공식 한도 없음 |
| 위키백과 | 지수당 1~2회 | 분기 정기변경 뒤에만 | 없음 |

실패한 요청은 최대 3번 다시 보냄.

## 3. 교차검증 (verify.py)

같은 (종목, 날짜) 를 출처 2개 이상이 저장했으면 값을 비교함.

| 항목 | 내용 |
|---|---|
| 비교 값 | 종가(분할만 보정, 배당 미반영): 모든 출처가 같은 기준이라 주 비교 값. 허용 0.5%. 수정종가: 허용 1%, KIS 는 배당 미반영이라 빠짐 |
| 기준값 | 출처 값의 중앙값. 출처가 2개면 통화별 우선순위에서 앞선 출처 값 (미국 Alpaca, 한국 yfinance) |
| 출처 2개 이상 | `source = 'CONSENSUS'` 행 저장 (기준값, 출처 수, 최대 편차, VERIFIED / MISMATCH, 어긋난 출처). 출처별 행에 편차(%)와 VERIFIED / MISMATCH |
| 출처 1개 | 그 행에 SINGLE. CONSENSUS 행은 만들지 않음 |
| 다시 검증 | 수집으로 값이 바뀐 행은 표시가 비워져 다음 실행에서 다시 검증됨 |
| 발행 | 검증 결과가 바뀌면 `price_daily.verify_status` 도 다시 발행됨 (값은 출처 우선순위로 고른 그대로) |

```powershell
python -m backend.jobs.daily verify                                   # 남은 것만
python -m backend.jobs.daily verify --start 2026-01-01 --end 2026-09-30   # 기간 다시 계산
```

처음 백필 직후에는 검증할 행이 많아 몇 번의 prices 실행에 걸쳐 끝남. 결과의 `verify_*` 개수와 `notes` 의 `MISMATCH 티커 날짜: 출처` 로 확인.

## 4. KOSPI200·Nasdaq-100 구성종목 파일

Nasdaq-100 도 같은 방식임. 위키백과 Nasdaq-100 문서에서 구성종목 표가 빠져서(2026-10 확인) 위키백과로는 0개가 나옴. Nasdaq-100 정기 변경도 12월이라 11월까지는 같은 목록.

`backend/data/config/ndx.csv` 는 이미 들어 있음 (2026-10-04 stockanalysis.com Nasdaq-100 목록 101종목, 섹터·산업은 GICS 기준으로 `backend/data/config/gics_overrides.csv` 에 적어 둠). 따로 할 일 없음.

목록을 새로 받을 때 (12월 정기 변경 뒤 등):

1. https://stockanalysis.com/list/nasdaq-100-stocks/ 의 표 (Symbol, Company Name) 를 `backend/data/config/ndx_holdings.csv` 로 저장. 사이트 Download 는 유료라, 표를 복사해 같은 칸으로 만들어도 됨
2. `python backend/scripts/make_constituents_csv.py --index NDX --as-of 날짜` → `backend/data/config/ndx.csv` (섹터는 위키백과 S&P 500 표의 GICS → 보충표 → yfinance 순서)
3. `python backend/scripts/try_adapters.py constituents --index NDX` 로 100개 안팎인지 확인

KOSPI200:

KOSPI200 구성종목을 주는 무료 공식 API 가 없어서 KRX 에서 내려받은 표를 고정 파일로 씀. 정기 변경이 6·12월이라 12월 변경 전까지는 같은 목록.

## 5. 가치평가 valuation_daily

가격(`price_daily`)과 재무(`financials`)로 (종목, 날짜) 마다 시가총액·PER·PBR·ROE·배당수익률을 미리 계산해 둔 표. 칸은 `DB_설계.md` 4-6.

| 값 | 계산 (그날 `report_date <= 날짜` 인 재무만 씀, 선견 없음) |
|---|---|
| 순이익 TTM | 이어진 최근 4개 분기 순이익 합 (지배주주 순이익(분기) 우선, 없으면 당기순이익(분기)). 미국: SEC 3개월 값(4분기 = 연간 − 9개월 누적). 한국: DART 분기 값. 분기가 안 이어지거나 연간 값이 더 최근이면 연간 값 (`method` 에 표시) |
| 주식 수 | 그날까지 공시된 최근 유통주식수 (미국 dei:EntityCommonStockSharesOutstanding, 한국 stockTotqySttus 의 발행 − 자기주식). 가격은 분할 보정, 공시 주식 수는 아니어서 yfinance 분할 이력(`주식분할`)으로 맞춤 (`split_factor`) |
| market_cap | 실제 종가(close × split_factor) × 그날 주식 수 |
| per, eps_ttm | 시가총액 ÷ 순이익 TTM. 순이익 ≤ 0 이면 per 는 NULL. eps_ttm 은 close 와 같은 기준의 주당 순이익 (close ÷ eps_ttm = per). 주식 수가 없고 미국 EPS(희석·분기) 4개가 있으면 그것으로 |
| pbr, bps | 시가총액 ÷ 최근 자본총계 (자본 ≤ 0 이면 NULL) |
| roe_ttm | 순이익 TTM ÷ 평균 자본 (최근 자본과 1년 전 자본의 평균) |
| dps_ttm, dividend_yield | 미국 최근 4분기 주당배당금 합, 한국 최근 사업연도 주당배당금 (보통주). 수익률은 비율 (0.02 = 2%). 배당 기록이 없으면 NULL |

- 재무가 550일 넘게 새로 공시되지 않으면 그 값은 비움 (상장폐지·자료 없음).
- 증분: 지난 성공 이후 값이 바뀐 가격·재무 행의 가장 이른 날짜부터 다시 계산하고, 값이 바뀐 행만 씀 (`updated_at` 그대로). 분할 이력이 바뀌면 그 종목 전체.
- 전체 다시 계산: `python -m backend.jobs.daily valuation --full` 또는 `backend/scripts/backfill.py --what valuation --valuation-full`.
- 분석 쪽(M3-04 `pe_ttm`·`roe_ttm`·`dividend_yield_ttm`)은 `financials` 로 직접 계산하지 않고 이 표를 `date <= as_of` 로 읽어도 됨.

## 6. 긴 백필 (PC, backend/scripts/backfill.py)

GitHub Actions 는 한 번에 몇 분이라 10년치를 한꺼번에 받지 못함. 처음 한 번은 PC(Windows, Python 3.11 이상)에서 Lightsail DB 로 직접 받음. Actions 정기 수집은 그대로 둬도 됨 (같은 키는 값이 바뀐 행만 쓰고, 테이블마다 PostgreSQL 잠금으로 순서를 맞춤. 백필 두 개를 동시에 돌리는 것만 막음).

```powershell
python backend/scripts/backfill.py                                   # 전부: GICS → 가격(빈 곳만) → 재무 12년 → 분할 → 가치평가 → 뉴스
python backend/scripts/backfill.py --what gics                       # GICS 분류·KSIC·사업 설명만 (7절)
python backend/scripts/backfill.py --what financials,valuation       # 재무·가치평가만
python backend/scripts/backfill.py --what news --lanes NAVER_NEWS,ALPACA_NEWS
python backend/scripts/backfill.py --what news --lanes GOOGLE_RSS_KR --markets KR --max-minutes 180
python backend/scripts/coverage_report.py                            # 결과 확인 (읽기 전용)
```

- 언제 멈춰도 됨 (Ctrl+C, `--max-minutes`). 같은 명령을 다시 돌리면 끝난 부분은 건너뜀 (진행은 DB 의 `fetch_log` 가 기억).
- 키가 없는 출처는 건너뛰고 처음에 알려 줌.
- 옵션: `--no-profiles` (gics: 사업 설명 안 받음), `--years 10` (가격·가치평가·뉴스), `--fin-years 12`, `--markets KR,US`, `--lanes`, `--max-minutes`, `--valuation-full`, `--rss-interval 1.5`, `--db 주소`.

예상 요청 수·시간 (미국 약 520종목 + 한국 200종목):

| 단계 | 요청 수 | 시간 | 비고 |
|---|---|---|---|
| GICS | KSIC: DART 기업개황 회사당 1회 × 200, 사업 설명: yfinance 종목당 1회 × 약 720 | 10~15분 (`--no-profiles` 면 1~2분) | 한 번 받은 종목은 다시 안 받음 |
| 가격 | 빈 곳만 | 이미 10년이 있으면 몇 분 | |
| 재무 DART | 회사당 약 105회 × 200 ≈ 2만1천 | 3~5시간, 하루 한도(2만) 때문에 이틀 | 한도가 차면(status 020) DART 만 멈추고 다음 단계로. 다음 날 같은 명령 |
| 재무 SEC | 종목당 1회(companyfacts) × 520 | 30~60분 (내려받기 약 1GB) | `SEC_USER_AGENT` 필요 |
| 분할 이력 | 종목당 1회 × 720 (yfinance) | 10~20분 | |
| 가치평가 | 계산 + 약 170만 행 쓰기 | 30~90분 (DB 왕복) | 다음부터는 바뀐 행만 |
| 뉴스 NAVER_NEWS | 종목당 최대 10회(최신 1000건) × 200 = 2,000 | 10~20분 | 검색 API 가 날짜 검색을 못 해 종목당 최신 1000건이 한계 |
| 뉴스 NEWSAPI | 종목당 1회 (최근 29일 100건) | 하루 남은 한도만큼 (아래) | 무료 플랜은 최근 1개월만. 더 오래된 기사는 유료 플랜 필요 |
| 뉴스 ALPACA_NEWS | 종목 × 11년 × 쪽(50건) ≈ 6천~3만 | 1~3시간 | 2015년부터 Benzinga 기사 |
| 뉴스 Google RSS | (200 + 520)종목 × 121달 ≈ 8만7천 | 1.5초 간격이면 약 36~50시간 | 달마다 `after:`/`before:` 검색, 최근 달부터. Google 이 막으면(429·503) 그 줄만 멈춤 → 몇 시간 뒤 다시 |

- NewsAPI 무료 플랜은 하루 100회를 정기 수집(`NEWS_DAILY_LIMITS` 의 NEWSAPI=90)과 나눠 씀. 백필은 오늘 이미 쓴 요청을 빼고 쓰므로, 정기 수집이 돈 날은 몇 건만 받음. 빨리 채우려면 며칠 동안 Actions Secret 의 `NEWSAPI=0` 으로 두고 백필을 매일 한 번 (약 520종목 ÷ 95 ≈ 6일).
- Google RSS 는 오래 걸리므로 `--lanes GOOGLE_RSS_KR,GOOGLE_RSS_US --max-minutes 600` 처럼 나눠 돌려도 됨. 같은 달을 모든 종목에 대해 끝낸 뒤 그 전 달로 가므로 중간에 멈춰도 종목 간 균형이 맞음. 달마다 Google 이 주는 기사는 100건 안팎이 한계.
- 백필은 `NEWS_PER_TICKER_DAY` 상한을 적용하지 않음 (받은 기사 모두 저장, 같은 주소는 한 번만).

## 7. GICS 분류 (classification.py)

종목마다 GICS 4단계(섹터 2자리·산업그룹 4자리·산업 6자리·세부산업 8자리)를 정해 `assets.gics_*` 에 두고, 어디서 정했는지를
`assets.gics_source` 에 남김. 분류표는 `backend/data/reference/gics_taxonomy.json` (2023-03 개편판, 한국어 이름은 프로젝트 번역) → DB `gics_taxonomy`.
`jobs meta` (구성종목 갱신 뒤)와 `backend/scripts/backfill.py --what gics` 가 돌림. 분류 자체는 인터넷 없이 정해짐.

| 순서 | 미국 종목 | 한국 종목 |
|---|---|---|
| 1 | `WIKIPEDIA_SP500`: 최신 S&P 500 스냅샷 행의 GICS Sub-Industry | `KR_MAP_REVIEWED` / `KR_MAP_DRAFT`: `backend/data/config/kr_gics.csv` (reviewed=true/false) |
| 2 | `OVERRIDE`: `backend/data/config/gics_overrides.csv` | `OVERRIDE`: `backend/data/config/gics_overrides.csv` 의 `.KS` 줄 |
| 3 | `NDX_FILE`: 최신 Nasdaq-100 스냅샷 (`backend/data/config/ndx.csv`) | `KR_MAP_KSIC_AUTO`: DART 기업개황 `induty_code`(KSIC) → `backend/data/config/ksic_to_gics.csv` (가장 긴 앞자리) |
| 4 | | `CONSTITUENT_KOSPI200`: 구성종목 행의 세부산업 이름이 GICS 면 그것 |
| 5 | `YAHOO_FALLBACK`: yfinance 프로필 섹터만 (세부산업 모름) | 같음 |
| 6 | `CONSTITUENT_<지수>`: 구성종목 행의 섹터 이름만 | 같음 |

- 세부산업을 못 정한 종목(5·6 이나 아무것도 없음)은 결과 `failed`, `fetch_log`(`GICS`, `gics:assets`, PARTIAL), `coverage_report.py` 4절에 이름이 나옴.
- 이번에 못 정해도 저장된 분류는 지우지 않음. ETF·지수는 대상 아님. 값이 바뀐 칸만 쓰고 그때 `gics_updated_at` 을 바꿈.
- KSIC(`assets.ksic_code`)·사업 설명(`business_summary`, yfinance `longBusinessSummary`)은 없는 종목만 받음 (meta 는 한 번에 60·30개까지, 백필은 전부).
  `DART_API_KEY` 가 없거나 yfinance 가 없으면 그 부분만 건너뜀.
- `ksic_to_gics.csv` 에서 지주회사(64992)처럼 코드가 빈 앞자리는 자동으로 정하지 않음 (사람이 `kr_gics.csv` 에 적음).
- 끝에 `index_constituent.gics_sub_industry_code` 가 빈 행을 채움: 행의 이름으로 풀리면 그 코드, 아니면(예전 한국 스냅샷의 Yahoo 이름) 그 종목의 현재 GICS 로 섹터·세부산업 이름과 코드를 바꿈.
- `coverage_report.py` 4절: 시장 × GICS 섹터별 재무·PER·뉴스 커버리지. 금융 섹터(40)는 매출액·영업이익 항목이 없는 것이 정상이라 매출액 칸이 '해당 없음'.

## 8. 종목 검색용 사전 (backend/scripts/build_descriptor.py)

```powershell
python backend/scripts/build_descriptor.py                           # SP500·NDX·KOSPI200·ALL, 스냅샷 날짜마다
python backend/scripts/build_descriptor.py --universe ALL --latest   # ALL 의 최신 버전만
```

- DB 만 읽음 (`assets`, `index_constituent`, `gics_taxonomy`; 읽기 전용 연결이라 `myfinsight_read` 주소도 됨). 인터넷·LLM 안 씀.
- 출력: `backend/data/processed/<universe>_descriptor_<스냅샷 날짜>.json` (버전), `<universe>_descriptor.json` (최신 복사본), `<universe>_descriptor_versions.json` (목록).
  내용이 같으면 다시 쓰지 않음 (`generated_at` 유지).
- 종목마다: `asset_id`, 티커, 이름, 시장·통화, 속한 지수, `gics` (4단계 코드·영문·한국어 이름), `gics_source`, `gics_asof`
  (`snapshot` = 그 스냅샷 당시 분류, `current` = 당시 분류가 없어 현재 분류), `keywords` (GICS 이름·단어, 회사명 단어, 티커),
  `intro` (사업 설명 첫 문장, 없으면 "<회사>은(는) <세부산업> 기업이다."), `intro_source`, `flags`.
- 버전 날짜 D 에는 지수마다 D 이전(포함) 가장 최근 스냅샷을 씀. 그런 스냅샷이 없으면 가장 오래된 스냅샷을 쓰고
  종목 `flags` 와 `limitations` 에 "당시 구성종목 미확보" (생존 편향 가능).
- 읽는 쪽: `backend.pipeline.descriptor` 의 `select_version(폴더, 유니버스, 기준일)` 로 버전을 고르고 `Descriptor.load(경로)` →
  `filter_by_gics(["4530"])` (접두 코드), `search_keywords(["반도체", "gpu"], min_distinct=1)` (단어 경계, 한국어 조사 허용),
  `sector_name_to_code("정보기술")`, `parents_of("45301020")`, `by_ticker("005930.KS")`.
