**평가에서 찾아 고친 문제 세 가지** (고친 뒤 다시 채점, §7)
1. **적립일 수익률 정의가 Module5 명세와 달랐다.** 매달 적립하는 시나리오에서 납입일 수익률이 납입금 비율만큼 작게 계산됐다. 추천안 100개 중 25개에서 화면의 CAGR·최대낙폭이 0.1~0.4%p 달라지는 크기였다. 지수를 평가액과 납입금으로 다시 계산하게 고쳐, 6번이 17.8점에서 20점이 됐다.
2. **수정안 비교 문서에서 최대낙폭의 장단점이 거꾸로 나왔다.** 덜 빠진 수정안이 '단점'에 들어갔다. 고쳐서 다시 실증했다(R10).
3. **서버 상태 응답과 DB 오류 메시지에 팀 DB 서버 주소가 그대로 나왔다.** 지금은 저장소 종류와 한국어 안내만 내보낸다. 옛 기록도 내보낼 때 주소를 지운다.

**3번·5번을 목표 위로 올린 것** (2026-11-07~08, §7.2)
1. **프롬프트를 다시 짰다.** 02·04·06·09·14a·14b·14c 를 '어떤 순서로 생각하는가 → 해야 할 것·하지 말 것' 꼴로 바꿨다.
2. **아이디어의 뜻을 코드로 거른다.** 배당 성장·안정 이력, 부채비율, 초대형주 순위, 이익률(같은 유니버스 중앙값 이상), 미국 법인, 고배당·저PER 의 유니버스 중앙값 기준선(사용자 결정), 모멘텀·저변동성 자격선.
3. **리포트가 조건을 점검한다.** 못 맞춘 조건마다 그 조건을 맞춘 최선 후보와 대가, 순위 규칙에서 밀린 이유, 지금 구성과 백테스트의 차이, 시장 국면을 사실로 넘긴다.
4. **시나리오를 대화부터 다시 돌리고 같은 기준표로 다시 심사했다.** 3번 3.74 → **4.16**, 5번 88.7% → **95.2%**. 5번은 목표선 바로 위다(§4·§5).

**남은 큰 일**
1. **사용자 평가(8번)를 하지 않았다.** 사람 10명 이상의 사용 평가가 남은 가장 큰 일이다. 3번·5번의 'Human Feedback'도 사람이 아닌 LLM 심사로만 매겼다.
2. **아이디어 번역의 남은 흠.** 테마 판정이 흔들린다(비슷한 회사를 다르게 판정, 예시를 범위로 읽음 — 5번 E1 89.5%). 배당 이력 판정은 팀 DB 의 주당배당 빈 곳과 주식 분할 미반영 때문에 오래 배당한 종목을 빼거나 분할을 '삭감'으로 본다.
3. 팀 DB 자료 빈 곳이 남아 있다. 주당배당(가치평가 표: CVX 는 2022년부터, XOM 은 없음), 선정 지표·시가총액 빈 곳 때문에 뽑힐 수 있던 종목이 빠진 경우가 있다.
4. 일부 실패 메시지에 영어 내부 오류 문장이 그대로 나온다.

### 1.3 채점 규칙

- 항목 달성률 = 측정값 ÷ 목표치 (1을 넘으면 1). 3번·8번은 평균 점수 ÷ 4.0.
- 한 항목에 측정이 둘 이상이면(예: 수집 성공률과 정량값 일치) **낮은 쪽**을 쓴다.
- 항목 점수 = 달성률 × 비중. 종합 점수 = 항목 점수의 합(100점 만점).
- 측정하지 못한 항목(8번)은 0점으로 넣고, 그 항목을 뺀 환산 점수를 따로 적는다.

- **기업별 근거가 빈 리포트 1개(077)** — 기업별 근거 단계가 7종목 중 1종목만 쓴 답을 통과시켰다. 평가 뒤 '선정 종목마다 카드 하나' 검사를 더했다(§6).
- **잘 된 점**
  - 결론이 세 조건(허용 낙폭·목표 수익·비교지수)을 점검하고, 못 맞춘 조건마다 그 조건을 맞춘 대안과 대가를 밝힌다. 논리적 일관성이 3.23 → 4.00 으로 가장 많이 올랐다.
  - 위험 고려가 가장 높다(4.40). 허용 낙폭 초과, 지금 구성의 주식 비중으로 환산한 낙폭, 집중 위험을 대체로 분명히 알린다.
  - 인용 근거는 모두 색인에 있고, 기준일 이후 근거는 없다(R8·R15).

'Human Feedback' 은 들어 있지 않다. 사람이 리포트 5개 정도를 같은 기준표로 매겨 LLM 점수와 맞춰 보길 권한다(§5).

**점수**: 평균 4.16 → 달성률 min(1, 4.16 ÷ 4.0) = 1.00 → **15.0 / 15** (처음 3.74 → 14.0)

### 3.6 Backtest 정확성 및 재현성 — 비중 20%, 목표 99%

평가 방법(원문): 기준 전략을 동일 입력 반복 실행 / 핵심 결과값 일치, 동일 입력 결과 재현율 측정.

처음 평가에서 적립일 수익률 정의가 명세와 달라 17.8점을 줬다. 그 부분을 고친 뒤 같은 시험을 다시 돌려 다시 채점했다. 아래 표는 두 번의 결과를 함께 적었다.

**재현성** — 실행 100개의 백테스트 입력(선정 종목, 목표 비중, 날짜별 비중, 기간, 자본·적립, 리밸런싱 규칙)을 그대로 넣어 백테스트 엔진을 두 번 새로 돌렸다. 돌릴 때마다 가격을 DB 에서 다시 읽었다. LLM 은 쓰지 않았다.

| 비교 | 처음 평가 (고치기 전 엔진) | 고친 뒤 |
| --- | --- | --- |
| 새로 돌린 1회차 ↔ 2회차 | 1,456 / 1,456 같음 | **1,457 / 1,457 같음** |
| 1회차 ↔ 2회차의 검증·추천 결과 | – | 100 / 100 같음 |
| 원래 실행에 저장된 결과 ↔ 새로 돌린 결과 | 1,456 / 1,456 같음 | 적립이 없는 34개 실행(488개)은 같음. 적립이 있는 66개 실행은 고친 만큼 달라짐(아래 '고친 영향') |

비교한 값은 최종 평가액, CAGR, 기간 수익률, 비교지수 대비 초과 CAGR, 최대낙폭, Sharpe, 일별 지수 전체, 리밸런싱 횟수다. 모두 소수점까지 똑같았다. 고친 뒤 포트폴리오가 1개 늘어난 것은 054 에서 낙폭 맞춤안이 하나 새로 생겼기 때문이다(아래). 백테스트 한 번은 가운데값 4초가 걸렸다.

**정확성 ① 계산 확인** — 엔진과 상관없이 따로 짠 계산으로 다시 셌다.
- 헤드라인 지표: 일별 지수에서 기간 수익률·CAGR·연변동성·최대낙폭·Sharpe 를 다시 계산 → 처음 7,280개, 고친 뒤 **7,285개 모두** 엔진 값과 같다.
- 일별 수익률: 전날 종가 기준 보유 비중 × 그날 종목 수익률(DB 수정종가, 달러 환산)의 합을 엔진 지수의 그날 수익률과 비교 → 거래가 없는 날은 처음·고친 뒤 모두 100% 같다(고친 뒤 1,045,819건, 최대 차이 0.000000000000001).

**정확성 ② 명세와 맞는가**

*처음 평가에서 찾은 문제* — 거래가 있는 날(리밸런싱·적립일)에만 차이가 있어 원인을 찾았다. 매달 적립하는 시나리오에서 엔진(bt 라이브러리의 가격 지수)은 납입금을 '그날 장 시작부터 있던 돈'으로 보고 그날 수익률을 계산했다(`r = V_t / (V_{t-1} + C_t) − 1`). 그런데 엔진은 납입금을 그날 **종가**에 산다. Module5 는 "엔진의 실제 적립 시점에 맞는 정의 하나를 적용한다"고 정했으므로, 종가 납입에 맞는 식(`r = (V_t − C_t) / V_{t-1} − 1`)을 써야 한다. 그때 방식은 납입일의 수익률을 납입금 비율만큼 작게 만들었다.
- 명세대로 계산한 값과 CAGR·최대낙폭이 화면 표시 단위(0.1%p) 안에서 같은 포트폴리오: 1,456개 중 1,283개(88.1%).
- 추천안만 보면 100개 중 25개에서 화면의 CAGR 또는 최대낙폭 숫자가 달라지는 크기였다.

*고친 것* — 지수를 bt 가격 지수 대신 평가액과 납입금으로 다시 계산한다(종가 납입 식, `backtest_engine.extract_raw`). 그동안 bt 지수의 희석을 메우려고 종목 기여도 계산에 넣었던 보정은 필요 없어져 뺐다(`backtest_metrics.linked_contribution`). Module5 §4 에 "지금 엔진은 거래일 끝 식을 쓴다"는 한 줄을 더했다. 모의투자는 원래 종가 기준으로 납입금을 계산하고 있어 바꾸지 않았다.

| 시험 | 처음 평가 | 고친 뒤 |
| --- | --- | --- |
| 엔진 지수 ↔ 평가액·납입금으로 따로 계산한 명세 식 지수 | 88.1% (표시 단위 안) | **1,457 / 1,457 같음 (차이 0)** |

## 5. 이 평가의 한계

- **자기 평가다.** 채점 기준을 만들고 측정한 쪽이 이 프로그램을 함께 만든 Claude 다. LLM 심사도 Claude 에이전트가 했다(리포트를 쓴 모델과는 다르다).

## 부록 B. 측정을 다시 하려면

측정에 쓴 스크립트는 `docs/mvp/evaluation/scripts/` 에 있다. 레포 루트에서 `PYTHONPATH=.` 로 실행한다. 실행 기록(`docs/mvp/scenario_qa/runs/`)과 단계 산출물(`output/`)은 저장소에 없고 로컬에만 있다.

| 스크립트 | 하는 일 |
| --- | --- |
| `measure.py` | 항목 1·2·4·7 과 요구사항 근거(질문 수, 리포트 12항목, 인용, 단계 기록, 선견)를 실행 100개에서 계산 |
| `metric_missing.py` | 선정 지표 빈 곳을 '자료 없음'과 '정의 안 됨'(적자·자본 음수)으로 나눔 |
| `yahoo_check.py` | DB 가격을 원 출처(yfinance)와 일별 수익률로 대조 |
| `bt_repro.py` | 저장된 백테스트 입력으로 엔진을 두 번 다시 돌려 결과 비교 |
| `engine_check.py` | 지표·일별 수익률을 엔진과 따로 다시 계산 |
| `bt_regrade.py`, `regrade_summary.py` | 고친 엔진으로 6번 다시 채점 (재현·명세 대조·재계산·추천 변화) |
| `flow_impact.py` | 적립일 수익률 정의 차이가 CAGR·최대낙폭에 주는 영향 |
| `packets.py`, `packets_e5.py`, `rule_rubric.md`, `report_rubric.md`, `score_judges.py` | LLM 심사 자료·기준표·집계 (E5 다시 심사 포함) |
| `revision_e2e.py` | 수정 요청을 끝까지 돌려 원안 비교 확인 |
