# 시나리오 QA 버그 리포트 (2026-11)

`backend/test_scenarios/` 의 시나리오 100개를 **000번부터 2개씩** 실제 LLM 으로 돌리고, 결과물(단계별 산출물·리포트)을 직접 읽으며 찾은 버그와 고친 내용을 모은 문서다. 화면(`Front/`)은 고치지 않았고 서버 로직만 고쳤다.

- 실행 방법: `python -m backend.analysis.eval.run_scenarios --files backend/test_scenarios/scenario_000.json,backend/test_scenarios/scenario_001.json --answer all --llm api --out docs/mvp/scenario_qa/runs`
  - 질문에는 늘 첫 번째 보기로 답한다(팀원이 돌린 방식과 같음). 그래서 시나리오의 종목 수·상한이 답변으로 바뀔 수 있다 → 점검은 **확정된 요청** 기준.
- 점검: `python -m backend.analysis.eval.audit --names scenario_000,scenario_001` → `audit/<시나리오>.md` (요약 + 규칙 검사). 리포트 문장은 사람이 직접 읽는다.
- 고친 뒤 재확인: `run_scenarios ... --replay` (대화 없이 같은 확정 요청을 다시 실행, LLM 캐시 사용).
- 표기: **F번호** = 팀원 제보, **Q번호** = 이번 QA 에서 새로 찾은 것. 상태 = 고침 / 기록만(범위 밖) / 버그 아님(정책).

## 3. 라운드 0 — 시나리오를 돌리기 전에 고친 것

시나리오를 돌리기 전 읽기 전용 코드 조사(9갈래)에서 확실히 드러난 BL·뉴스 뷰 문제를 먼저 고쳤다. 뉴스 뷰 프롬프트가 바뀌므로, 시나리오를 돌린 뒤에 고치면 LLM 을 다시 불러야 해서 비용이 든다.

### Q-001 뉴스 뷰의 방향이 계산에서 뒤집힘 — 고침
- **증상**: "좋은 소식" 뷰인데 오히려 그 종목 비중이 줄어든다. 팀원이 말한 "비중 반영이 안 된다"의 주원인. 예: 시나리오 000 시작일에 "O 배당 인상 +3%"(사전 기대 16.8%) → 비중 −2.0%p, "ABBV FDA 승인 +4%"(사전 10.2%) → −3.2%p. 지난 실행 전체에서 절대 뷰 31%, 상대 뷰 18% 가 이렇게 뒤집혔다. 줄어든 비중은 뷰가 없는 저변동 종목(000 의 VZ 는 다섯 세트 모두 +3.3%p)으로 갔다.
- **원인**: Black-Litterman 은 뷰 숫자 Q 를 사전 기대수익 π 와 비교해 비중을 움직인다. LLM 은 "좋은 소식이니 +3%"처럼 작은 숫자를 쓰는데 π 는 10~25% 라서, 숫자가 π 보다 낮으면 계산은 "약세 뷰"로 읽는다 (`m4_portfolio/views.py`, `math.build_PQ`). 프롬프트에 "implied 보다 높으면 강세"라고 적었지만 코드가 강제하지 않았다.
- **고친 방법**: LLM 은 이제 `direction`(up/down)과 `strength`(weak/medium/strong)만 낸다. 코드가 Q 를 만든다 — 절대 뷰 Q = π ± k·σ, 상대 뷰 Q = max(π_long − π_short, 0) + k·σ(long−short), k = 0.10/0.20/0.35 (`views._quantify`, 설정 `view_strength_k`). 뷰 문장은 "사전 기대 X% → 뷰 Y%" 로 보여 준다. 근거 1건 뷰의 신뢰도 상한 0.3, 같은 종목을 양쪽 다리에 둔 뷰 제거도 코드로 강제했다. 적중은 방향으로 판정한다.
- **테스트**: `test_scenario_qa.py::test_positive_view_raises_weight_and_negative_view_lowers_it`, `test_quantify_*`.

### Q-002 BL 최적화에 사후 공분산을 써서, 뷰가 약해도 최소분산 쪽으로 쏠림 — 고침
- **증상**: 뷰 신뢰도가 0 에 가까워도 BL 비중이 기준 비중으로 돌아오지 않는다. 뷰가 말하지 않은 종목들이 함께 움직였다(000: 뷰와 무관한 이동이 실제 변화와 상관 0.6~0.8).
- **원인**: 효용 최적화에 사후 공분산(Σ + M)을 넘겼다 (`black_litterman.py`). π 는 Σ 로 역최적화했으므로 Σ 로 풀어야 뷰가 없을 때 기준 비중이 정답이 된다. 문서(Module4)는 원래 Σ 다.
- **고친 방법**: 최적화는 사전 Σ 로. 예상 통계도 같은 Σ 로.
- **테스트**: `test_negligible_confidence_keeps_baseline_weights`.

### Q-003 위험회피 계수 δ 의 하한을 배수 뒤에 적용해 성향·허용 낙폭이 무시됨 — 고침
- **증상**: 급락이 추정 창에 든 날(지난 walk-forward 날짜의 41%, KOSPI 비교지수 70%)에는 보수·공격 성향과 허용 낙폭에 상관없이 δ 가 모두 1.5. 계산 조건 표에 "−0.17 × 1.5 × 1.33 = 1.5" 같은 틀린 식이 찍혔다.
- **원인**: `max(하한, 시장 δ × 성향 배수 × 낙폭 배수)` 순서 (`market_model.py`).
- **고친 방법**: `max(하한, 시장 δ) × 성향 배수 × 낙폭 배수`. 계산 조건 표는 "→ 하한 적용" 으로 표기.
- **테스트**: `test_delta_floor_applies_before_profile_multipliers`.

### Q-004 BL 최적화가 실패한 세트가 '뉴스 뷰' 이름으로 남음 — 고침
- **증상**: 최적화가 실패해 기준 비중을 그대로 쓴 세트도 카드에는 뷰 설명·사후 수익이 그대로 보였고, 기준 비중과 같은 성과라 동점이면 목록 순서 때문에 "뉴스 뷰" 이름으로 추천될 수 있었다. 세트 하나만 실패해도 전체를 "기준 비중 유지"로 표시했다. 시작일 BL(10)과 walk-forward 첫날(10w)이 같은 LLM 단계명을 써서 프롬프트·응답 기록이 서로 덮어썼다.
- **고친 방법**: 실패한 세트는 "(뷰 미반영)" 으로 이름 붙이고 설명·사후 수익을 정리, 백테스트 후보에서 뺀다. 기준 비중 유지는 모든 세트가 실패했을 때만. walk-forward 는 날짜별 최적화 실패 메시지를 남긴다(`optimizer_notes`). 단계명은 `_start` / `_wf` 로 분리.
- **테스트**: `test_failed_optimizer_marks_set_without_view_text`, 기존 `test_rebalance_regressions.py`.

### Q-005 뉴스 뷰 적중률에 12개월이 끝나지 않은 뷰까지 섞임 — 고침
- **증상**: "구성 뒤 12개월 기준" 적중률에 몇십 일짜리 창도 판정에 들어갔다(어떤 실행은 55건 중 44건이 330일 미만).
- **고친 방법**: 12개월이 안 끝난 뷰는 "판정 보류"(hit 없음)로 두고 적중률에서 뺀다. 체크포인트의 "지금까지" 진단은 사전 기대를 기간에 비례해 비교한다.
- **테스트**: `test_view_hit_follows_direction_and_waits_for_full_window`.

- **R9·현금 설명·선정 불가 사유가 상한 원인을 따로 판단** — 두 상한이 다 걸리는 경우(002: 2종목 × 25% + 섹터 35%)를 섹터 탓으로만 썼고, 선정 불가 사유는 섹터 상한이 묶을 때도 '2개뿐이라 50%까지' 라고 썼다(실제 30%). 섹터 상한 34%·66% 처럼 5 의 배수가 아니면 '필요한 섹터 상한' 탐색이 100% 를 건너뛰었다. → 공용 판단(`common/capacity.py`: 종목당 / 섹터 / 둘 다)을 R9·`cash_breakdown`(새 `cash_by_caps_cause_ko`)·`infeasibility.cause_ko`·'구성 불충분' 원인이 같이 쓴다. 두 상한이 다 걸리면 "섹터 상한만 올리면 50%까지만 오르고 …" 까지 적는다.

#### Q-128 시가총액비중이 섹터 상한에 걸리면 시가총액 순서를 깸 (애플 = 팔란티어) — 고침 (030, 높음)
