# Module3. 종목 선정과 전략 생성

전체 구조: [Module_prototype_v2.md](Module_prototype_v2.md)

## 1. 역할

이 모듈은 사용자의 아이디어를 종목 검색 조건으로 바꾸고, 후보 중에서 정량 기준에 맞는 종목을 선정한다. 어떤 종목을 왜 골랐는지 설명할 수 있도록 검색·분류·순위와 제외 사유를 남긴다. 다음 구성 단계에 넘길 전략 사양도 여기서 정한다.

LLM은 아이디어 해석, 후보의 테마 적합성 분류와 근거 설명에 사용한다. 후보 검색과 최종 순위는 코드가 결정한다. 테마 분류는 LLM 응답에 영향을 받지만, 응답 캐시를 재사용하면 같은 입력의 결과를 재현할 수 있다.

## 2. 입력과 출력

| 구분 | 내용 |
| --- | --- |
| 입력 | 확정 요청, 이전 이력 요약, 기준일별 종목 검색 사전, 금융 자료와 뉴스 근거 |
| 출력 | 의도 해석, 후보 목록, 테마 분류, 최종 선정 종목, 전략 사양, 기업별 근거 문단 |
| 다음 단계 | Module4가 비중 계산에 사용하고 Module5가 선정 과정과 근거를 리포트에 사용 |

## 3. 처리 흐름

### 아이디어를 검색 조건으로 바꾸기

`stage2_intent.py`가 요청, 자연어 아이디어와 이전 이력 요약을 LLM에 전달한다. 산업분류는 GICS 트리의 코드·이름·종목 수로 제공하고 전체 종목표는 주지 않는다.

LLM은 아이디어를 하나 이상의 테마로 정리한다. 각 테마에는 설명, 산업 코드와 검색 키워드를 붙인다. 선정 템플릿, 지표 방향, 위험 해석, 뉴스 비중 조정의 상한, 검증 기준과 설명 수준도 함께 반환한다. 정해지지 않은 조건은 질문으로 반환하고 Module1이 사용자에게 확인한다.

사용자가 지정한 템플릿과 수치 제약은 그대로 유지한다. 이전 이력과 다른 해석이 필요하면 조건을 바꾸기 전에 질문한다. GICS 코드 자릿수와 템플릿·지표 일치를 검사하고, 유니버스에 없는 예시 티커는 제거해 기록한다.

의도 결과에는 `interpretation`, `exclude_theme_rules`, `screen`, `risk_params`, `news_tilt`, `validation_criteria`, `report_settings`, `questions`를 둔다. `screen`은 지표·정렬 방향·종목 수와 테마 적합성 하한을 담는다. 손실이 발생하면 매도하려는 사용자에게는 허용 낙폭을 보수적으로 해석할 수 있으나, 적용한 실효 기준은 조건 확인과 결과에 명확히 남긴다.

### 후보 검색과 필수 조건 적용

`stage3_retrieve.py`가 기준일의 사전에서 산업 코드 접두 일치와 키워드 일치를 검색한다. 키워드는 종목명, 키워드와 소개 문장의 단어 단위로 비교한다. 키워드만으로 포함된 종목은 서로 다른 키워드가 두 개 이상 일치해야 한다.

기존 구현은 예시 티커 일치도 검색 근거로 사용한다. 이를 유지한다면 예시 티커가 최종 선정 명령처럼 작동하지 않도록 같은 데이터·제약 검사를 적용하고, 어떤 경로로 후보가 됐는지 남겨야 한다. 예시 티커 경로를 제거할지는 확인 사항이다.

후보에 제외 종목·섹터·테마, 자산 유형, 최소 시가총액, 최근 60거래일 평균 거래대금과 가격 이력 조건을 적용한다. 필수 포함 종목은 포함 요청으로 다루되, 제외 조건 충돌이나 필수 데이터 누락을 무시하지 않는다. 필수 종목이 실제로 포함될 수 없으면 이유를 반환한다.

시가총액은 기준일에 이용 가능한 발행주식수와 종가의 곱으로 근사하고 한국 종목은 USD 환산한다. 평균 거래대금도 USD로 계산한다. 발행주식수의 발표·기준 시점을 확보하지 못하면 과거 시가총액의 한계로 기록한다.

후보가 목표 종목 수보다 적으면 산업 범위를 한 단계 넓혀 한 번 더 검색한다. 120개를 넘으면 일치 규칙 수와 거래대금을 기준으로 줄인다. 필수 포함 종목이 이 제한으로 탈락하지 않도록 한다. 동률 정렬에는 티커 같은 안정적인 기준을 사용한다.

검색 결과에 `matched_by`, `matched_keywords`, 제외 사유와 단계별 후보 수를 남긴다. 과거 기준일에는 Module2의 해당 날짜 사전 버전을 사용한다.

### 테마 적합성 분류

`stage4_classify.py`가 후보를 40개씩 묶어 LLM에 전달한다. 입력은 티커·이름·산업분류·사업 소개·일치 키워드와 테마 설명이다. 응답에는 티커별 테마 포함 여부, 관련 테마, 신뢰도, 한국어 사유와 제외 테마 해당 여부를 받는다.

통과 조건은 테마에 해당하고, 신뢰도 하한 이상이며, 제외 테마에 걸리지 않는 것이다. 응답에 누락된 후보는 경고와 함께 미통과 처리한다. 입력에 없던 종목을 응답으로 추가할 수 없다. 배치 순서가 판정 기준을 바꾸지 않도록 프롬프트와 출력 검사를 구성한다.

테마 신뢰도는 LLM의 분류 점수다. 실제 투자 수익의 확률이나 검증된 성공 확률로 설명하지 않는다.

### 정량 순위와 최종 종목 선정

`stage5_screen.py`와 `metrics.py`가 테마를 통과한 후보의 지표를 계산한다. 모든 지표는 기준일에 이용 가능한 자료만 사용한다.

| 템플릿 | 지표 | 선정 방향 |
| --- | --- | --- |
| 모멘텀 `momentum` | `return_12m_1m = P(t−21) / P(t−252) − 1` | 높은 순 |
| 저변동성 `low_volatility` | `vol_60d`: 60거래일 일수익률 표준편차 × √252 | 낮은 순 |
| 저PER `low_per` | `pe_ttm`: 주가 / 이용 가능한 최근 4분기 EPS 합 | 낮은 순 |
| 퀄리티 `quality` | `roe_ttm` | 높은 순 |
| 고배당 `high_dividend` | `dividend_yield_ttm` | 높은 순 |

모멘텀 가격은 수정주가 기준이다. EPS가 0 이하인 종목은 PER 결측으로 처리한다. ROE와 배당수익률은 DB 항목과 계산 정의를 고정해야 한다. 가격과 재무의 통화·주식 단위도 맞춘다.

지표가 없는 일반 후보는 제외한다. 필수 포함 종목은 유지하고 결측 사유를 남기지만, 이후 비중 계산에 필요한 자료까지 부족하면 실행을 중단해야 한다.

목표 종목 수를 기준으로 순위를 선택하면서 섹터 분산을 고려한다. 기존 방식은 섹터당 선호 수를 `floor(섹터 상한 × 선정 수)`로 정해 우선 선발하고, 부족하면 미뤄 둔 후보로 채운다. 이는 종목 수에 대한 선호이며 실제 비중 상한을 보장하는 검사는 아니다. 실제 제약은 Module4에서 적용한다.

섹터별 선정 수를 k라고 할 때 전액 주식 배분 용량은 `Σ min(k × 종목 상한, 섹터 상한)`으로 검사한다. 1보다 작으면 구성 불가능 사유와 조건 변경 선택지를 반환한다. 통과 종목이 0이면 중단한다. 최소 종목 수 미달은 정상 선정으로 숨기지 않고 기록하며, Module5의 필수 조건 검증에서 통과할 수 없게 한다.

최종 전략 사양에는 선정 방식·지표, 종목 수, 기준 비중 방식, 리밸런싱 규칙, 제약과 비교지수를 담는다. 이후 리포트와 모의투자는 이 사양을 사용한다.

### 기업별 근거 설명

`stage6_explain.py`가 선정 결과와 DB 근거를 LLM에 전달한다. 종목마다 뉴스 근거, 재무 값, 선정 지표와 순위를 제공하고 인용 식별자를 붙인다. 재무와 계산 지표에도 뉴스와 구분되는 근거 식별자를 부여해야 한다.

설명은 대체로 2~4문단으로 작성한다. 확인 가능한 사실, 그 사실의 해석, 투자 아이디어와의 연결, 실제 선정 기준을 구분해 서술한다. 사실 주장은 인용으로 연결하고, 숫자는 전달한 값과 대조한다.

자료가 적으면 설명을 줄이고 확인 가능한 지표 중심으로 쓴다. LLM의 일반 지식이나 주가 상승만으로 기업의 경쟁력을 단정하지 않는다. 선정 후 읽은 뉴스를 정량 선정의 원인으로 설명하지 않는다. 뉴스가 실제로 비중 조정에 사용됐는지는 Module4의 기록으로 확인한다.

## 4. 단계 산출물

모든 파일은 `output/<run_id>/`에 저장하고 공통 `request_id`, `stage`, `warnings`를 포함한다.

| 파일 | 주요 내용 |
| --- | --- |
| `02_intent.json` | 테마, 검색·선정 규칙, 위험 해석, 뉴스 조정 상한, 검증 기준, 질문 |
| `03_candidates.json` | 후보, 일치 근거, 제외 사유, 검색 단계별 종목 수 |
| `04_tagging.json` | 후보별 테마 판정, 신뢰도, 사유, 통과 목록과 배치 기록 |
| `05_selection.json` | 최종 종목, 순위, 지표, 섹터, 강제 포함 여부, 거절 사유, 구성 가능성, 전략 사양 |
| `06_selection_explained.json` | 기업별 근거 문단과 인용 목록 |

Module4는 의도·선정 결과·전략 사양을 사용한다. Module5는 후보가 줄어든 과정, 실제 선정 기준과 기업별 근거를 결과와 리포트에 포함한다.

## 5. 과거 선정과 재사용 조건

백테스트 시작일에는 Module4가 이 모듈의 후보 검색과 정량 선정을 당시 기준으로 다시 실행한다. 사용자 테마와 선호는 재사용할 수 있지만 현재 시점의 재무·사업 정보가 과거 판정에 들어가지 않게 해야 한다.

원문은 현재 후보 분류를 과거 선정에 재사용하도록 적었지만, 과거 사전에서 새 후보가 나오면 현재 분류 결과에 해당 종목이 없을 수 있다. 새 후보를 무조건 미통과로 처리하면 과거 유니버스를 사용한 의미가 줄어든다. 같은 자료 버전으로 분류된 후보만 재사용하고, 새 후보는 과거 자료로 분류하거나 그 자료를 확보할 수 없다는 한계를 남기는 처리가 필요하다. 실제 재분류 범위는 구현 전에 확정한다.

## 6. 구현 상태와 완료 기준

후보 검색, 후보 분류와 정량 선정은 원문에서 구현된 것으로 기록되어 있다. 가격·재무 조회는 Module2로 교체한다. 의도 해석에는 이전 이력과 질문을 추가하고, 기업별 설명은 필수 단계로 바꾸어 근거 인용을 연결한다.

- 같은 자료·캐시·조건에서 같은 후보와 정량 순위가 나온다.
- 사용자 제약과 선정 템플릿을 LLM이 바꾸지 않는다.
- 모든 후보의 통과·제외 사유가 남는다.
- 구성 불가능과 최소 종목 수 미달이 후속 검증에 전달된다.
- 기업별 설명의 숫자와 인용이 실제 자료에 연결된다.
- 과거 선정에 사용한 자료 버전과 분류 재사용 범위를 기록한다.
