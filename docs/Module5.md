# Module5. 백테스트, 검증과 리포트

전체 구조: [Module_prototype_v2.md](Module_prototype_v2.md)

## 1. 역할

이 모듈은 구성된 전략을 과거 시장에서 시뮬레이션하고, 성과와 위험이 사용자 조건에 맞는지 검사한다. 이후 선정 근거, 구성 방식, 성과와 한계를 하나의 리포트로 만든다. 수정 요청이면 원안과 수정안을 같은 조건에서 비교한다.

계산과 검증은 코드가 수행한다. LLM은 검증된 결과를 해석하고 문단으로 설명한다. 조건에 맞는 포트폴리오가 없다는 결과와, 계산·문서 생성 자체가 실패한 상태는 구분한다.

## 2. 입력과 출력

| 구분 | 내용 |
| --- | --- |
| 입력 | 요청·의도·선정 결과, 기업별 근거, 시작일 목표, 날짜별 비중 경로, 현재 구성, 가격 패널과 설정 |
| 출력 | 백테스트와 지표, 조건 판정, 비교 우선안·대안, 통합 결과, 수정안 비교, 리포트 |
| 사용처 | Module1의 이력, Module6의 전략 선택, Module7의 결과 화면 |

## 3. 백테스트 실행

### 공통 조건

포트폴리오와 비교지수는 같은 기간, 초기자본과 월 적립 조건으로 실행한다. 가격은 Module2의 USD 환산 `adj_close` 패널을 사용한다. 한국 종목이 있으면 한국 시장의 보조 비교지수도 제공할 수 있으며, 실제 지수 또는 추종 ETF의 선택은 확인이 필요하다. 상대 성과 판정은 사용자가 지정한 비교지수를 기준으로 한다.

기존 엔진은 종가 체결, 소수 주식과 bp 단위 수수료를 가정한다. 공매도, 레버리지, 세금과 슬리피지는 포함하지 않는다. 배당·기업행동은 수정주가에 반영된 것으로 간주하고 별도 배당 현금흐름을 중복 추가하지 않는다. 수정주가로 계산한 가상 수량을 실제 거래 가능한 수량과 혼동하지 않도록 한다.

### 적립과 리밸런싱

고정 목표 포트폴리오는 리밸런싱일마다 시작일에 정한 목표 비중으로 복원한다. 날짜별 재구성 포트폴리오는 Module4가 해당 날짜에 계산한 비중을 적용한다. 마지막 날은 매매 대신 종료 체크포인트를 남긴다.

적립은 매월 `contribution_day` 이후 첫 거래일에 수행한다. 적립금을 당시 적용 가능한 목표 비중에 따라 가상 매수한다. 같은 날 적립과 리밸런싱이 겹치면 자본 반영·주문·수수료의 순서를 고정해 중복 거래가 생기지 않게 해야 한다.

목표와 실제 적용 비중은 수수료 때문에 차이가 있을 수 있으므로 둘 다 저장한다. 비교지수도 동일한 납입 조건으로 매수 후 보유한다. 비용 적용 범위와 체결 시점은 명시한다.

### 날짜별 기록

일별 평가액, 수익률과 낙폭을 저장하고, 리밸런싱일과 종료일에 체크포인트를 만든다. 체크포인트는 조정 전·후·목표 비중, 보유, 거래, 회전율과 비용, 구간 성과와 누적 지표, 적용한 의견과 근거를 담는다.

적립 원장, 월별·연도별 성과, 낙폭 사건과 종목별 기여도도 기록한다. 투자 의견의 예상과 실현을 비교할 때는 의견 생성일, 평가기간과 연율 변환을 맞춘다. 평가기간이 끝나지 않은 의견은 적중 여부를 확정하지 않는다.

252거래일 미만이면 `annualized_reliable`을 false로 두고 기간 수익률을 함께 제공한다. 연환산 수치는 참고 값으로 표시한다.

## 4. 성과 지표

### 납입금과 운용 성과 구분

적립금이 있는 평가액에 `V_t / V_(t−1) − 1`을 그대로 적용하면 납입금을 투자 수익으로 계산하게 된다. 원문의 단순 평가액 수익률 식은 외부 현금흐름이 없을 때만 사용한다.

백테스트는 자금 유입·유출과 운용 수익을 분리한 시간가중 수익률을 계산해야 한다. 현금흐름을 거래일 시작에 반영한다면 단순 일별 식은 `r_t = V_t / (V_(t−1) + C_t) − 1`이고, 거래일 끝에 반영한다면 `r_t = (V_t − C_t) / V_(t−1) − 1`이다. 엔진의 실제 적립 시점에 맞는 정의 하나를 적용한다.

기간 수익률·CAGR·변동성·Sharpe와 MDD는 이 운용 수익률에서 계산한다. 납입 합계, 최종 평가액과 이익은 금액 지표로 따로 제공하고, 납입 시점을 반영한 투자자 수익률은 XIRR로 계산한다. 이 원칙은 Module6의 모의투자에도 동일하게 적용한다.

### 지표 목록과 정의

| 구분 | 지표 |
| --- | --- |
| 수익 | 기간 수익률, CAGR, 최고·최저 월수익률 |
| 위험 | 연변동성, 하방편차, MDD, 고점·저점·회복일, 최악 일수익률, 왜도·첨도 |
| 위험조정 | Sharpe, Sortino, Calmar |
| 비교지수 대비 | 초과 CAGR, beta, alpha, 상관, 추적오차, 정보비율, 상승·하락 포착률, 월별 우위 비율 |
| 기준 비중 대비 | 초과수익과 active risk |
| 구성 | 유효 종목 수, HHI, 상위 종목 기여, 평균 섹터 비중, 최대 비중 이탈과 상한 위반 |
| 거래 | 리밸런싱 수, 평균 회전율, 수수료 합계 |
| 안정성 | 12개월 롤링 지표 |
| 금액 | 납입 합계, 최종 평가액, 이익, XIRR, 최대 손실과 최악 12개월 손실 |

연변동성은 일수익률 표준편차 × √252로 계산한다. MDD는 외부 현금흐름을 제거한 누적 운용 지수의 고점 대비 하락률이며, 검증에서는 양수 손실 크기로 비교한다. 회복하지 못한 낙폭의 회복일은 없음으로 둔다.

기존 명세의 Sharpe 정의는 `(CAGR − 무위험수익률) / 연변동성`이다. 이 정의를 유지할 경우 결과에 계산 방식을 표시한다. 산술평균 초과수익을 사용하는 Sharpe로 변경하려면 기존 결과와 검증을 함께 바꿔야 한다. 변동성이 0이면 Sharpe는 null로 두고 사유를 반환한다.

전체 기간과 체크포인트는 같은 `backtest_metrics.py`를 사용한다. 수치는 저장할 때 반올림하지 않는다. 합집합 시장 달력에서도 연 252일을 쓰는 가정은 Module2의 정책과 함께 확인한다.

## 5. 사용자 조건 검증과 비교 우선안

`stage12_validate.py`는 계산된 값을 고치지 않고 기준과 대조한다. 아래 V1~V8은 서비스 요구사항 번호와 혼동하지 않도록 붙인 검증 번호다.

| 규칙 | 내용 | 수준과 판정 |
| --- | --- | --- |
| V1 | 최대낙폭 | 필수: MDD ≤ 실효 허용 낙폭 |
| V2 | 목표수익 | 참고: CAGR ≥ 목표 연수익률; 1년 미만은 정보만 제공 |
| V3 | 비교지수 대비 | 참고: 초과 CAGR > 0 |
| V4 | 종목 비중 상한 | 필수: 리밸런싱 후 최대 비중 ≤ 상한 + 0.1%p |
| V5 | 섹터 비중 상한 | 필수: 리밸런싱 후 섹터 비중 ≤ 상한 |
| V6 | 종목 수 | 필수: 최소 종목 수 충족; 요청의 최대 수도 확인 |
| V7 | 변동성 적합성 | 참고: 성향별 변동성 범위 충족; 1년 미만은 정보만 제공 |
| V8 | 데이터 무결성 | 필수: 시계열 길이와 리밸런싱 기록 일치 |

필수 규칙은 pass·fail, 참고 규칙은 pass·warn, 판단하기 어려운 짧은 기간의 항목은 info로 저장한다. 포트폴리오 상태는 필수 실패가 있으면 fail, 참고 미달이 있으면 warn, 모두 충족하면 pass다. 보유 중 시장 움직임으로 발생한 비중 이탈은 목표·리밸런싱 후 상한 위반과 구분한다.

필수 실패가 없는 포트폴리오 중 Sharpe가 가장 높은 것을 비교 우선안으로 정한다. 동률이면 MDD가 작은 것을 선택한다. Sharpe를 계산할 수 없는 후보의 선택 정책은 확정해야 한다. 내부 결과 필드 `recommendation`을 사용하더라도 리포트에서는 과거 평가 조건에서의 비교 결과로 설명한다.

통과안이 없으면 그 사실과 규칙별 실패 수를 그대로 제공한다. 현금 수익률 0을 가정한 혼합 대안을 만들 때에는 허용 낙폭 안에 들어오는 최소 현금 비중을 탐색한 뒤 같은 엔진으로 실제 시뮬레이션한다. 현금이 데이터 오류나 종목 수 부족을 해결하는 것으로 처리해서는 안 된다. 대안도 전체 규칙을 다시 확인한다.

과거 MDD 조건을 충족했다고 미래 손실이 제한되는 것은 아니다. 손실 감내 기준을 자동 손절 규칙으로 바꾸지 않는다.

## 6. 결과 통합과 수정안 비교

`stage13_collect.py`가 앞선 산출물을 `ResultsBundle`로 묶는다. 요청, 의도, 선정·근거, 시장모형·기준·의견·목표·현재 구성, 백테스트, 조건 판정, 원화 환산, 출처, 설정, LLM 사용량과 단계별 문제 기록을 포함한다.

통합 과정에서는 금융 지표를 다시 계산하거나 임의로 반올림하지 않는다. 원화 표시용 환산 곱셈만 수행한다. 포트폴리오 식별자, 시계열 길이, 환산표와 출처 연결을 검사해 `13_results.json`과 DB `run_artifact`에 저장한다.

수정안은 원안과 기간·초기자본·적립·비교지수·리밸런싱 규칙이 같은지 검사한다. 같은 조건이 아니면 공정한 비교 결과를 만들지 않고 이유를 반환한다. 조건 변경, 추가·제외·유지 종목, 비중·규칙 차이와 수익·위험 비교표를 저장한다. 장점과 불리한 점의 문단은 선택적으로 LLM이 작성하되 표의 값만 사용한다.

비교 파일은 `store/data/comparisons/<comparison_id>.json`이다. 필드는 `schema_version`, `comparison_id`, 양쪽 run·report ID, 생성 시각, `same_window`, `condition_changes`, `ticker_changes`, `weight_changes`, `rule_changes`, `performance_table`, `pros_cons_ko`, `warnings`다.

## 7. 리포트 생성

### 수치 블록과 설명 문단

`report_blocks.py`가 통합 결과에서 KPI, 표, 차트, 구성 계산 과정과 출처를 만든다. 선택 포트폴리오는 비교 우선안이며, 없으면 기준 포트폴리오를 설명하되 조건 통과안이 없다는 점을 본문에 명시한다.

첫 LLM 호출은 사실 요약을 받아 성과·위험·조건 적합성·뉴스 의견의 효과를 해석한다. 두 번째 호출은 사실과 해석을 바탕으로 종합 판단, 산업·시장 설명, 구성 이유와 재검토 조건을 문단으로 작성한다. 종합 판단은 보통 3~5문단, 기업별 근거는 Module3의 문단을 사용한다. 자료가 부족한 산업 분석을 일반 지식으로 채우지 않는다.

### 리포트의 일곱 섹션

| 순서 | 섹션 | 내용 |
| --- | --- | --- |
| 1 | 종합 투자 판단 | 아이디어와 조건, 핵심 성과·위험과 적합성 |
| 2 | 산업과 시장 분석 | DB 자료에 기반한 사실과 해석 |
| 3 | 기업별 투자 근거 | 선정 과정, 지표와 기업별 인용 문단 |
| 4 | 포트폴리오 구성과 운용 | 비중·배분, 제약 적용 과정, 현재 구성과 리밸런싱 |
| 5 | 과거 성과와 해석 | KPI, 누적수익·낙폭, 체크포인트, 날짜별 재구성, 조건 판정과 대안 |
| 6 | 판단의 전제와 재검토 조건 | 자료 부족, 가정, 편향과 다시 확인할 조건 |
| 7 | 참고자료와 분석 조건 | 출처, 적용 파라미터, 실행 기록과 용어 |

한 페이지로 이어지는 문서와 섹션 이동 메뉴를 제공한다. 위험은 반복 경고 배너 대신 관련 본문과 전제 섹션에서 설명한다. 과거 가상 성과의 미래 비보장 설명은 자연스러운 본문 문장으로 포함한다.

### 문서 검증

LLM 문단의 수치는 전달한 사실 목록과 대조한다. %·%p·USD·KRW와 자리수 변환을 고려하고, 날짜와 근거에 포함된 숫자도 출처와 연결한다. 단순히 같은 숫자가 결과 어딘가에 있다는 것만으로 통과시키지 말고 대상·기간·단위가 맞는지 확인해야 한다. 구현은 수치 참조 방식과 텍스트 검사 범위를 정해야 한다.

인용 ID가 실제로 존재하는지, 기업과 날짜가 맞는지, 금지된 단정 표현이 있는지도 검사한다. 오류를 끝내 해결하지 못하면 공개 가능한 리포트로 저장하지 않고 run을 FAILED로 처리한다. 통과 포트폴리오가 없다는 정상 분석 결과는 리포트에 남기지만, 수치·인용 검증에 실패한 문서를 정상 리포트처럼 보여 주지는 않는다.

| `11_daily_panel.parquet` | 사용한 일별 가격 패널 |
| `12_validation.json` | 기준, 판정, 비교표, 비교 우선안, 대안과 요약 |
| `13_results.json`, DB `run_artifact` | 통합 결과와 실행 조건 |
| `14_report.json`, DB `report` | 검증을 통과한 리포트 문서 |

리포트 객체는 헤더, KPI, 이동 메뉴, 섹션 블록, 데이터셋, 평가, 출처, 설정과 상태를 포함한다. 블록 종류는 paragraphs·kpis·table·donut·line·area·bar·funnel·callout·cards·checkpoints·glossary·evidence다. 표에는 pct·usd·krw·text·url 같은 형식 태그를 붙이고 실제 표시 반올림은 화면이 수행한다. 생성한 리포트는 수정하지 않고 재분석 때 새 문서를 만든다.

## 9. 구현 상태와 완료 기준

기존 `stage11_backtest.py`, `backtest_engine.py`, `backtest_metrics.py`, `stage12_validate.py`의 계산 코드는 원문에서 구현됨으로 기록되어 있다. DB 조회와 공통 달력 연결이 필요하다. `stage13_collect.py`에는 DB 저장과 수정안 비교를, `stage14_report.py`에는 일곱 섹션과 출처 검증을 연결한다. 프롬프트는 `14a_interpret`와 `14b_narrate`를 사용한다.

- 적립금이 운용 수익률로 계산되지 않는다.
- 포트폴리오와 비교지수의 평가 조건이 같고, 종료 체크포인트와 최종 지표가 일치한다.
- 필수 규칙 실패가 있는 포트폴리오를 비교 우선안으로 선택하지 않는다.
- 조건 통과안이 없다는 결과가 리포트에 드러난다.
- 수정안 비교가 같은 평가 조건을 사용한다.
- 모든 리포트 수치와 인용이 검증되고 일곱 섹션이 존재한다.

구현 전 확인할 항목은 현금흐름의 반영 시점, 당일 자료로 만든 비중의 체결 지연, 혼합 시장 휴장 자산의 주문 처리, Sharpe null 후보의 선택 방식이다. 같은 종가를 보고 그 종가로 거래했다고 가정하는 문제는 과거 자료만 조회했다는 검사만으로 해결되지 않는다. 정보 마감과 체결 시점을 별도 조건으로 고정해야 한다.
